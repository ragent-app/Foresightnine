# Public-test abuse-control assumptions

**Status: pending security and operations review/approval. Not evidence of public launch readiness.**

Phase 8 assumes that public testing is protected by layered controls. The product is not considered ready for public launch merely because a UI path works locally.

## Required controls

- IP and anonymous-session rate limits enforced server-side, with Redis (or an approved equivalent) for distributed counters, short-lived cache, and job state;
- per-session, per-IP, and global daily model-call quotas with hard ceilings and cost budgets;
- CAPTCHA or an equivalent risk-based challenge before expensive or abuse-prone operations;
- request-body, thesis, evidence, URL, upload, SSE, and job-size limits;
- authentication and authorization checks for any non-anonymous resource, with UUIDs generated by an approved cryptographically secure implementation and validated at service boundaries;
- SSRF-safe URL handling: no automatic fetching of user URLs from the client, and server fetches only through an allowlisted, bounded, content-type-checked path;
- prompt-injection and content-safety handling for user text, evidence excerpts, and provider output;
- idempotency keys for chargeable or state-changing operations, cancellation and retry limits, and replay-safe SSE events;
- secret scanning and redacted logs; no provider key, CAPTCHA secret, Redis credential, session secret, or personal data in bundles, fixtures, telemetry, or error messages;
- dependency, container, CORS, CSP, and mobile release-signing checks before distribution.

## Assumptions and failure behavior

The client must assume that the network, model provider, search capability, Redis, CAPTCHA, and market-data provider can fail. A failed or unavailable dependency must return an explicit unavailable state, not fabricated candidates, evidence, probabilities, prices, or current allocations. If freshness cannot be established, current Public Default amounts are disabled and only clearly labelled historical/simulated research may remain visible.

Controls are defense in depth, not a guarantee against abuse. Operations must set thresholds, alert owners, escalation contacts, and retention limits before enabling public traffic. Security review must confirm that CAPTCHA and rate-limit bypasses, replay, enumeration, credential stuffing, prompt abuse, SSRF, oversized payloads, and denial-of-service scenarios have test evidence.
