HTTP 400 的安全诊断仅为 `error_object`、code `unknown`、category `unknown`。服务端错误清洗只接受固定标准 code/type 白名单，且不保留 `param`；`unknown` 既可能表示对应字段缺失，也可能表示值不在白名单，不能据此判断服务商原始 code/type/param。默认传输针对非 2xx 只保存清洗结果并丢弃响应正文，私有 stderr 为空，没有可用原始响应可供进一步核实。当前证据不能确认 400 根因，也不能证明该部署支持或不支持原生工具。

本目录的 `fed.json` 和 `fed-reconciliation.json` 是受限私有记录，可能包含研究运行上下文，不应作为公开成果；不将续接内容导出。结果不证明阶段 B 研究质量或投资效果，后续排查需要单独设计、固定变量和调用记录。

## 请求参数与待修正边界

实际请求记录显示 `max_tokens=193040`。代码将账户剩余额度减去输入预估后作为单次请求输出上限；这是账户额度与请求参数的耦合，不是用户或预登记设置的任务 token 预算。官方 [GLM-5.3-Flash 模型说明](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash) 标注最大输出为 128K，但 Coding 端具体适用范围尚未实证。该差异是 HTTP 400 的首要排查方向，并不能证明拒绝的原因；错误 code、type 和 param 因上述清洗与正文未保存而无法确定。

后续应将账户额度与单请求输出参数分开处理：依据部署明确验证的协议能力与支持参数决定是否发送及如何约束输出上限；能力未知时如实处理，不按模型品牌或本次数值硬编码，也不把账户额度自动当成用户任务预算。后续安全诊断应在不暴露敏感正文的前提下保留可核查的错误字段信息。
