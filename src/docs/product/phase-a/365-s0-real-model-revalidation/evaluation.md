# 365 S0 修复的真实模型复验（E1）：结果

2026-11-20 按[预登记](preregistration.md)执行。

- **代码与环境**：镜像 `foresightnine-api:s0-9434192`，96 个应用文件与提交 `9434192` 逐字节一致（见 `scripts/image-app-sha256.txt`）。运行在隔离的 compose 项目 `foresightnine-revalidation-365` 中，模型、搜索、数据源配置与线上相同。
- **记录**：每次运行的导出在 `results/<标签>/`，驱动和评估脚本在 `scripts/`。
- **口径说明**：评估脚本的自动判定有一处逻辑错误：可评估的运行不足时，它把 C3、C4 判成“不通过”，而这种情况应为“无法判定”。下文的判定由人工依据导出记录和检查点重新核对。

**执行偏差**（如实记录）：

1. **会话中断**：主会话在 Q-B1 进行中被中断，驱动脚本随之停止，但 Q-B1 在服务端继续运行并正常完成。之后用同一标签恢复轮询并导出，没有重复提交。剩余运行改为脱离会话执行。
2. **资源争用由我方造成**：Q-A3 与 Q-B3 运行期间，我在同一台主机（2 个 CPU 核心、3.8 GB 内存，同时承载线上服务）上让子 Agent 跑全量测试。主机负载平均达到 43，导致容器内数据库连接和 DNS 解析超时，两次运行因此失败。这违背了预登记中“运行中不改动环境”的本意，是本次实验执行上的失误。两次运行的检查点完整保留，下文只把检查点中已经发生的工具结果作为证据，不推断运行如果没中断会怎样。
3. **未补跑**：按预登记，所有运行都没有补跑。

## 判定

| 编号 | 判定项 | 结果 | 依据 |
| --- | --- | --- | --- |
| C1 | 时效（Q-A） | **通过（2/3）** | Q-A1、Q-A3 都取得了实际最后日期为 2026-11-19 的 QQQ、SPY 行情（Q-A3 另有 ONEQ），两次的开场说明都写了“截至 2026-11-19（最近已完成交易日）”。Q-A2 在任何工具调用前就因模型服务超时结束，无法评估。说明：Q-A3 后来因基础设施失败中断，但取到行情发生在中断之前。 |
| C2 | 时效（Q-B） | **未通过（1/3）** | 只有 Q-B3 取了 QQQ 2026-11-13 到 11-19 的数据作为大盘对照（11-19 约下跌 2.2%，与新闻报道一致）。Q-B1、Q-B2 没有调用行情工具，是模型的选择，不是工具失败；两份报告都说明了行情工具不覆盖 ANT。 |
| C3 | 只读失败不中止 | **通过（6/6）** | 没有任何运行因只读来源失败而结束。多次出现的单个来源失败（Reuters 401、tickeron 403、SEC S-1 获取失败、CNN 页面过大），都只记为该来源失败，研究继续进行。结束原因分别是模型服务错误、模型服务超时、基础设施故障和正常提交。 |
| C4 | 无进展误判 | **通过，但未被触发** | 6 次运行中没有出现“同一批里既有重复请求又有新请求”的情况，也没有任何 `no_progress` 结束。修复逻辑本身在真实运行中没有被检验到。 |
| C5 | 失败可修正 | **未触发** | 6 次运行都没有发生行情工具失败：模型一开始就请求了允许范围内的日期（截至最近已收盘交易日）。原线上的失败模式没有再出现，但带提示的重试路径没有被真实检验。 |
| C6 | 报告注明数据日期 | **通过（2/2）** | 两份完成的报告（Q-B1、Q-B2）都依据研究时钟写明“最近已完成交易日为 2026-11-19”“价格数据截至 2026-11-19 收盘”，并据此判断用户说的“今天”并不是 IPO 首日。 |

**结论**：

- **时效问题已解决**：模型按研究时钟理解“最近”和“今天”，行情工具取到了最近一个已收盘交易日的数据。原线上的失败模式，即只取到 2025 年数据、行情请求因“交易时段未确认”被拒，没有再出现。只读来源失败也不再中止研究。
- **C2 未通过的性质**：原因是模型没有主动取大盘对照，不是工具问题。这属于取证策略层面的问题，计划用 S2 的“IPO 与重大事件首日”方法包解决（证据需求清单里包含“大盘对照”）。
- **有效样本偏少**：6 次运行中有 3 次因外部服务或我方造成的资源争用中断，实际可用的样本少于预登记。上述结论只适用于这次的条件，不能推广为“修复在所有条件下有效”。研究质量也没有评估。

## 发现的问题

1. **提交被拒时没有指明是哪条引文出错（已修复）**：Q-A1 的 17 条引文里只有 1 条有误，它把 `614.31000 USD` 写成了 `614.31 USD`。报错没有说明是哪一条，模型反复改写那些本来正确的引文，浪费了 5 次调用和约 25 万 token，直到运行因模型服务错误结束。Q-B1、Q-B3 也出现过类似情况，例如原文用弯引号而模型写成直引号。修复见提交 `9c053f9`：现在会列出每条失败引文的序号，给出原文中最接近的文本和可直接照抄的建议引文。复验所用的镜像不包含这次修复。
2. **大型 HTML 和申报文件仍受 5 MB 上限限制**：CNN 页面“过大”，SEC 的 S-1 申报文件获取失败。大文档管线目前只覆盖 PDF。按方案第 6.14.5 节，超长 HTML 和申报文件也应按章节切分、按需读取，这一点列入后续工作。
3. **用量汇总显示为 0（原有问题）**：只要有一次模型调用的用量未知，轮次汇总的 token 就记为 0（例如 Q-A1 实际已记账 755,987）。这是改动前就存在的统计逻辑，会误导用户，需要单独修复。
4. **上下文压缩仍然频繁**：Q-A1 压缩了 6 次，每次都重置了前缀，缓存命中率 56%；Q-B 系列分别是 74% 和 83%。压缩回落线的效果还需要更多样本才能判断。
5. **模型服务稳定性**：两次运行（Q-A1、Q-A2）因模型服务的流式错误或空闲超时结束。这部分在我方控制之外，但说明长任务需要更好的部分成果交付和续跑体验。
6. **实验执行**：在这台小型主机上，实验期间不能并行运行重负载任务。今后的实验要等实验结束后再跑测试，或者把实验放到独立的主机上。
