## 362 修复项在真实运行中的表现

1. **发出前失败自动重试**：A1 的 2 次 DNS 失败被挽回，本轮完成；A2 首次请求和 4 次重试（等待 1、2、4、8 秒）全部在发出前失败，重试用尽。
2. **事实记录参数**：A1 第一次仍漏填 `value`，收到“Invalid arguments: facts[0].value: required field is missing; …”后下一次即成功（362 需要纠正两次）。
3. **停止原因文案**：A2 以 `provider_timeout` 结束，界面对应“模型服务请求超时”（已有单元测试；本次截图未截到该提示块）。
4. **跳转链接**：本次 5 条线索中没有跳转链接；搜索结果本身与 362 不同，不能单独归因于修复。
5. **重复交付**：本次没有出现“已提交的部分完成”轮次，未覆盖。
6. **研究模型名称**：`/v1/account` 返回 `research_model: glm-5.3-flash`。
7. **SEC 能力**：能力接口返回 SEC 未配置；本次线索中没有 SEC 链接，界面行为未覆盖。

## 发现的问题

1. **“继续研究”和“交付已有成果”在真实后端上必定失败**（阻断）：后端边界要求所有 POST 带 `Content-Type: application/json`，而界面对不带请求体的 POST（`/continue`、`/recover`）不设该头，返回 415。模拟后端没有这条规则，所以此前的测试和浏览器验收都没发现。
2. **连接失败的根因是每次请求都做的 DoH 校验**：本机代理把 `api.z.ai` 解析为假地址 `198.18.0.10`，传输层因此在每次模型请求前向公共 DoH 服务再发两次 HTTPS 查询（A、AAAA，各 5 秒超时）来确认真实地址是公网地址，结果不缓存。容器内单独测量 20 次：耗时 2 至 6 秒，1 次超时；运行中此类失败成串出现，记录为“dns”阶段失败。系统 DNS 本身在测量中 20 次全部成功、几乎不耗时。
3. **研究 Agent 保存的计算没有 `input_status`**，要等用户下一次保存版本时才由后端补算。
