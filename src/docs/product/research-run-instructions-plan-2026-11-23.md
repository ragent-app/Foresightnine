# 研究自动推进与运行中追加指令实施方案

**状态**　已在本地工作区实施并完成阶段验收，待发布。开发基线为 2026-11-23 本地 master 的 `59a9895`。本方案取代此前让用户点击“继续研究”或手动取回成果的交互设计。

## 一　用户发起一次，Agent 负责做到交付

用户提出研究问题后，可以离开页面，也可以随时在原输入框追加要求。Agent 负责追踪原题和后续要求、查找证据、核验结果、处理可恢复中断并交付。只要还有获准且有望解决核心问题的新动作，研究就继续。用户无需判断何时重试、何时换检索方法或何时保存成果。

**前台状态只表达这轮工作的进度。** 已受理至最终结果落库期间显示“研究中”；正常收尾并能读到最终交付后显示“已完成”；用户主动停止显示“已停止”。“部分完成”留作内部证据覆盖信息。已完成的报告可以得出“现有资料无法验证该问题”这一结论，必须说明核查过什么、限制在哪里。若系统故障导致连可读交付都没有，显示具体服务错误和已知恢复情况，恢复后再切到终态，避免提前给出成功回执。

| 页面 | 研究中 | 已完成 | 已停止 |
| --- | --- | --- | --- |
| 主题页与侧栏 | 显示当前活动，例如“正在核对两端股数”；关闭页面后服务端继续工作 | 打开最终版本。先给能回答的结论，再在相关结论旁写明局限 | 标明用户停止，展示此前保存的证据和最后进度 |
| 输入区 | 可追加指令，保留独立“停止研究”按钮 | 可选追问，自成新轮；阅读即可结束 | 可显式要求恢复或发起新轮 |
| 研究记录 | 可看消息回执、工具进度、阶段成果 | 可看来源、调用、预算、已尝试路径和仍未核实项 | 可看停止位置及已发生的调用 |

只有扩大预算、改变权限或提供用户独有资料等确需本人决定的事项才给可选入口。先完成其余获准工作，按现有边界交付。常规收尾不等待用户点击。

## 二　Apple 样本的一次完整体验

1. 用户问“分析 Apple 的市值变化”。研究已取得价格和一份年报，页面显示“研究中 · 正在核对股本”。若模型此时提交只含股价的答案，协调器发现市值仍是核心缺口，自动继续。
2. 用户可以追加“用两端日期的已发行股数，不要用加权平均股数”。页面立即确认收到。正在执行的请求正常返回，下一次模型决策纳入这项更正。即使用户从未发送补充，原题本身也要求核对股数。
3. Agent 优先定位已有年报中的股数原文和披露日期。若该材料只能覆盖一个时点，再按获准来源查另一端。核验股数口径、交易日期和价格口径，满足条件后分别计算两端市值与变化，报告关联两端证据和计算。
4. 若合理路径已查尽，最终版本显示“已完成”。例如可以写“2025 年 11 月 20 日至 2026 年 11 月 20 日，Apple 收盘价从 266.25 美元升至 342.56 美元，上涨 28.66%。两端股数尚未取得可与价格日期匹配的证据，因此无法核实同期市值涨幅。” 报告只列实际执行过的核查。这里的价格取自原主题，自动补查和最终呈现是待实现的样例。

验收再选一项无关任务，例如比较两家公司营业利润率。两类任务使用相同的继续判定，避免在代码里写入公司、指标或模型名特例。

## 三　后端如何决定继续还是交付

现有运行时已按模型、工具批次和游标循环。有一处关键断点：提交工具写入 `submission` 后可立即返回结果；检查点一旦带有已提交结果，恢复路径以交付该结果为主。前端随后才判断是否显示继续或恢复按钮。因此改造点应在写入最终提交之前，并配套服务端后台恢复。[提交工具](../../apps/api/app/research_tool_executor.py) · [运行循环](../../apps/api/app/research_runtime.py) · [恢复判定](../../apps/api/app/research_recovery.py)

| 协调器观察到的情况 | 服务端动作 |
| --- | --- |
| 所有有效核心要求已回答，证据、计算、引用通过校验 | 生成最终版本。可选延伸问题留在正文，不继续扩大任务 |
| 核心要求未回答，已有材料中仍有可读区域、待验证引文、可运行计算，或授权来源中有不同的取证路径 | 将模型提交保存为阶段草稿，把具体缺口和下一步依据返回当轮模型；优先使用已有材料，继续执行 |
| 超时、限流或服务重启，且已知之前的外呼结果或确认未发出 | 按现有重试与恢复规则处理，必要时延后调度。继续使用原轮已有工具结果、指令和用量 |
| 外呼可能已发出、结算未知 | 先依据既有回执和供应商支持的查询核对，禁止重放同一未知外呼。允许安全的本地整理；无法核对且无其他安全路径时交付可验证内容并记下限制 |
| 同一缺口重复尝试、证据未变化 | 查看是否还有实质不同的路径。有则转向；没有则写清已经核查的边界并交付。可重用已有无进展、重复截断和超时保护 |
| 用户设定的预算耗尽、来源权限不足、资料只由用户持有 | 允许剩余的本地计算、校验和保存；完成仍可回答的部分，在报告中说明受限结论。付费、提额或扩大来源必须服从用户原设置 |
| 用户点击停止 | 将停止意图持久化到整轮，取消排队接续，阻止新的外呼，尽力取消在途工作，保存已取得内容，迟到回调不得重启研究 |

**具体判定。** 交付检查读取同一个任务版本下的核心分项、用户指令、已有证据和可用工具。对每个待解决分项记录下一步动作、输入来源、预期可得到的证据和先前尝试结果。模型可以提出路径，服务端检查其可执行性、权限、预算、参数和是否已尝试。以缺口、工具、规范化输入、证据版本识别重复动作；同义改写、重排相同来源或模型声称“再试一次”不足以开启新一轮。新来源、新定位范围、已修正的日期或实质不同的方法可以支持继续。

**完成条件。** 每项有效核心要求都有已核验答案或有记录可查的限制，且没有仍可执行、有望带来新证据的核心动作。阶段草稿、工具收尾、待保存提交和等待可恢复重试均处于“研究中”。证据不足仍按现有证据口径保存；展示“已完成”仅在最终版本成功写入、能从主题读取后生效。用户没有设置运行预算时保持未设置，不为自动继续添加隐藏的次数、费用或时间上限。已有单次请求边界和无进展保护继续生效。

## 四　运行中追加 prompt

- **接收与顺序。** 新增按主题和逻辑研究轮授权的 `POST /v2/research/topics/{topic_id}/turns/{turn_id}/instructions`，请求体为 `{"text":"先核对两端股数"}`，沿用 `Idempotency-Key`。创建研究时返回稳定的 `turn_id`，后台接替操作不改变它。客户端拿到轮次标识前保留草稿。
- **接口回执。** 首次写入返回 201 和消息 ID、轮次、服务端序号、接收时间及正文；同键同文返回 200 和原回执（即使研究随后结束）。同键异文或新消息遇已关闭轮次返回可区分的 409；未认证、越权或资源不存在、正文无效分别为 401、404、422。单条长度建议为 4,000 个 Unicode 码点。网络超时重发复用原键，多标签按服务端顺序合并。
- **何时纳入。** 消息在请求构造前到达，可以进入当次；流式输出期间到达，在下次决策纳入。每个工具启动前原子比较计划所见指令序号。新指令先到则跳过尚未启动的旧调用，为每个原工具 ID 写入配对的“因用户更正而跳过”结果，已启动调用收尾并按实际结算。跳过的工具不计外呼。Agent 根据最新要求重排。
- **输入与交付。** 追加消息按真实用户来源进入统一模型输入；三种 wire API 都在正确配对的工具结果之后安放用户内容。系统恢复说明、外部资料和用户指令按来源编码。预算估算、压缩、重试和恢复使用同一输入版本；优先保留有效要求、否定条件、时间和口径。新指令可替代旧要求，审计保留原文和替代关系。模型提交及最终组装共同按有效要求核验，不凭模型复述就认定满足。[统一输入](../../apps/api/app/model_protocol.py) · [上下文组装](../../apps/api/app/research_context_manager.py) · [交付核验](../../apps/api/app/research_delivery.py)
- **用户可见反馈。** 收到后显示“已收到”，对应请求取得供应商响应后可显示“已纳入本次研究”；未知回执保留待确认。最终可从该条消息定位答案、证据或无法确认的原因。Enter 发送，Shift+Enter 换行，中文输入法选字不提交。发送失败保留草稿。
- **和结束同时发生。** 新消息先落库，旧候选不能封存，研究自动继续。最终封存先成功，则后到的消息保留在输入框，用户可作为下一轮追问发送。阶段提交始终保持接收开放。手动停止和消息争用同一轮次锁，已接收但未处理的消息保留记录。

## 五　后台接续、恢复与展示一致性

以 `turn_id` 表示用户的一轮研究，`operation_id` 表示一次具体执行。前端订阅轮次；一次操作的结束不能直接推导研究已完成。复用已有异步操作准入、持久化检查点、账户权限、版本乐观锁和 SSE。将当前 HTTP 继续与恢复入口的公共逻辑提取成应用服务，供后台在原账户授权边界内调用。[操作调度](../../apps/api/app/operations.py) · [API 与检查点](../../apps/api/app/main.py)

1. **持久化决策。** 按账户、主题和轮次保存当前执行、阶段、已用预算、待解决核心要求、已试路径、停止标记、指令序号、下次可执行时间、候选提交及最终版本引用。追加日志独立于会反复覆盖的运行快照，外呼回执按调用 ID 去重。自动续行跨操作累计用量、已用时间和原始截止时间，不能因接替重新取得一份预算。
2. **页面关闭后继续。** 正常情况在同一运行循环推进。必须等待或进程退出时，将下一步和检查点在同一事务持久化。后台调度器领取到期任务，用轮次、检查点修订和动作作为幂等标识，使用租约及递增代次防止两台 worker 同时外呼或旧 worker 写回。服务重启后扫描尚未结束且可接替的轮次。鉴权配置变化时重新核查，禁止自动切换到其他账户、模型或资料权限。
3. **完成与竞争。** 统一处理工具提交、文本直返、预算退出和异常退出。对可推进的候选存为草稿，返回当前循环或入队；对可交付候选，在与追加和停止相同的事务锁下核对任务序号、所有权和停止意图，再封存快照。版本写入幂等绑定轮次与封存修订，崩溃后自动补存；提交后未写版本时无需模型外呼。最终版本遇并发用户编辑时使用既有版本保护，避免覆盖用户判断。对账未决和不可恢复故障保留可诊断记录。
4. **读取。** 鉴权快照返回轮次状态、当前活动、最新指令回执、可展示的阶段证据及最终版本 ID。SSE 通知只是更新信号，刷新、重连和多标签页从快照重建；状态更新游标独立于消息序号。首页、侧栏、主题页、历史记录采用相同定义。历史版本固定当时的答案，证据展示仍受当前权限控制。普通查看不触发外呼。[主题页](../../apps/web/src/pages/TopicPage.tsx) · [答复组件](../../apps/web/src/pages/topic/Conversation.tsx) · [侧栏](../../apps/web/src/ui/Sidebar.tsx)
5. **既有研究。** 新行为适用于启动时接受该执行语义的研究。部署或打开历史主题不自动重新启动已结束的任务、产生模型费用或改写历史版本。旧主题可展示其已有证据和交付范围。本文的 Apple 样本用于说明新的运行机制。

## 六　实施顺序与验收

| 顺序 | 工程交付 | 出口 |
| --- | --- | --- |
| 1 | 区分逻辑研究轮、执行尝试、证据覆盖和最终版本。实现任务修订、指令日志、停止标记和共享的继续判定 | 原题与追加要求使用同一核验输入；`partial` 候选不会直接封存 |
| 2 | 接入运行循环、工具启动检查、三种协议适配和交付前复核，生成 API 契约及前端类型 | 单进程即可完成“自动补查 → 中途更正 → 交付” |
| 3 | 增加持久化后台接续、取消传播、原预算继承、未知外呼核对及幂等交付 | 无浏览器也可推进；两个 worker 和进程重启均不会重复已发出的工作 |
| 4 | 更新输入区、进度流、主题页、历史页和侧栏，将阶段草稿与最终答复分别呈现 | 页面无需“继续研究”按钮即可完成整条链路，只有可读取的最终交付显示“已完成” |

**首轮验收使用固定资料、可控模型和可计数工具。** 能分别暂停在请求构造、工具启动、提交、版本写入这四处，核对实际模型请求、工具回执、用量、指令序号和最终版本。以下为验收条件，实测范围见第七节。

| 场景 | 通过条件 |
| --- | --- |
| 模型提前提交，资料内还有核心证据 | 零次用户点击，Agent 自动补查，页面持续显示研究中，一份最终版本绑定核验依据 |
| 授权内证据确实不足；只有可选问题未答 | 前者交付含已试路径及结论边界的报告；后者及时交付。页面均显示已完成，未知数值不冒充已核验值 |
| 流式输出中连续追加两条；另一标签重发同键 | 当前流正常返回，下一次决策按序纳入；同键一条，已取代要求可追溯 |
| 工具批次中途更正、追加与封存竞争 | 在途调用只结算一次，尚未启动的旧调用零外呼，协议结果配对；竞争的两种时序都保留用户消息或草稿 |
| 已排队自动续行时用户停止 | 后续模型和工具启动数均为零；在途回执可结算，刷新仍显示已停止 |
| 两 worker、关闭所有标签、重启、最后一步写版本失败 | 服务端继续或自动补存，版本只交付一次；写入前不显示完成，旧 worker 不能覆盖新工作 |
| 同一动作反复无进展、临时限流、外呼结果未知 | 分别验证改用有效路径或收尾、延时接续、按回执核对；重复未知外呼数为零 |
| 显式零预算、跨操作耗尽预算、未设预算、无来源权限 | 原预算和权限对整轮生效；有本地可做的工作则完成；未设置时无默认总量上限 |
| 空历史、压缩和恢复后的三种协议 | 用户指令与工具输出来源、顺序、配对及预算估算正确；新增模型无须按品牌写分支 |
| 无指令、证据充足的基线；只读历史主题 | 基线研究一次提交即可交付；读历史主题不会启动新调用。跨账户不可见，导出尊重资料权限 |
| 完全无法写入交付，或只拿到未经核验的笔记 | 前者显示真实服务错误与恢复状态；后者只交付可说明的核查结果与限制。二者均无虚假成功或伪造结论 |

核对自动接续成功数、同一动作重复外呼数、预算消耗、最终版本写入失败数和核心缺口解决率。用户体验重点验证两件事：用户离开后能否收到结果，以及用户能否从报告区分有依据的结论和未确定的部分。后续真实模型实验固定资料、权限、参数和预算，发布依项目流程另行授权。

## 七　本次实施与阶段验收记录

前后端已接入同一逻辑轮次。宿主进程运行持久化接续调度器，网页只负责发送指令、停止及读取进度。完成标记与可读取的版本绑定。侧栏使用一次账户级批量查询。模型请求记录所见指令序号，界面区分已收、调用回执待确认、已纳入三种投递状态；最终答案另存证据、精确文本位置或未解决原因。

| 场景 | 实测结果 |
| --- | --- |
| 提前交稿，用户中途要求换口径 | 受控研究循环保留阶段草稿并接着检索、读取、记录事实、计算和交付。检查了旧工具结果配对、已读原文和追加指令的顺序；不同实体的搜索不会因为另一实体没有结果而被封锁。[场景用例](../../apps/api/tests/test_research_run_instruction_scenarios.py) |
