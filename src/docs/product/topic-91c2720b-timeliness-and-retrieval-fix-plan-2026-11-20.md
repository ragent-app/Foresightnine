### 1.4 上下文缓存：真正的命中率杀手

| # | 问题 | 证据 |

## 2. 关于“把时间放在开头，会不会导致缓存一个都无法命中”

结论：**放对位置就不会额外损失缓存；放错位置才会。** 实测下来，影响命中率的主要是 K1，不是日期字段。

Messages 协议的前缀缓存按 `tools → system → messages[0] → 历史 → 末尾` 的顺序逐字节匹配，某处一变，它后面的部分全部失效。

| 放的位置 | 对缓存的影响 | 结论 |
| --- | --- | --- |
| `system` 或 `tools` | 这两部分是目前唯一在各次运行之间完全相同的前缀（同一个 sha），放日期会让它按天甚至按次失效。放秒级时间戳最糟。 | **不要放** |
| `messages[0]`，即每次运行的初始 JSON 资料（`state['user']`），在运行开始时定值 | 这一段每次运行本来就不同（问题、来源清单、上一轮研究摘要都会变），多一个日期字段不增加任何失效。运行内它保持逐字节不变，后续调用照常命中。它保存在检查点里，续跑和恢复时用的也是同一份，不会变。 | **推荐** |
| 每次调用都刷新的末尾提示（`tail_note`） | 末尾内容本来就不进入可复用前缀，但每次调用都写“现在几点”没有意义，还会让同一次运行里模型看到的时间前后不一致。 | 不需要 |
| 工具返回结果（如 `latest_allowed_end_date`） | 属于追加在历史末尾的内容，不影响之前的前缀。 | 推荐，用来补充具体信息 |

落地规则：

1. 研究时钟在运行创建时生成一次，写入运行输入，作为 `messages[0]` 资料里的一个字段，续跑时直接沿用。
2. 用日期级粒度（UTC 日期，加上各交易所的当地日期和最近一个已收盘交易日），保留一个精确到分钟的 `captured_at` 方便审计。同一天里，同一个问题的初始资料除了 `captured_at` 外完全一致。
3. “怎么使用研究时钟”的规则写进 `SYSTEM` 的固定文字，不在里面放具体日期，`SYSTEM` 仍然可以跨运行缓存。
4. 时钟和 `research_as_of` 是两件事：时钟是“现在”，`research_as_of` 是用户指定的资料截止点（为空表示不设截止）。两个都要传给模型，但不要混用。

## 3. 修复项

优先级说明：P0 决定能否拿到最新数据、研究会不会被意外中止；P1 决定效率和结论是否准确；P2 是减少反复试错。

### P0-1 研究时钟（对应 T1）

- 运行创建时生成 `research_clock`：
  - `captured_at`：UTC，精确到分钟；
  - `utc_date`；
  - `exchanges[]`：每个已配置交易所的 `{exchange, timezone, local_date, last_completed_session}`。`last_completed_session` 先用简单规则：当地日期前一天，再跳过周末；遇到节假日，该日本来就没有数据，可以接受。之后有交易日历再替换。
- 时钟写进 `messages[0]` 的资料和运行输入，检查点恢复时沿用原值（`runtime_origin_captured_at` 已有类似语义）。
- 在 `SYSTEM` 加固定规则：
  - “最近”“当前”“今年”一律以 `research_clock` 为准，不用训练知识推断日期；
  - 报告必须写明各项数据截至哪一天。
- 上一轮研究摘要（`prior_research`）带上每个来源的数据截止日期，后续轮次能直接看出数据已经过时。

### P0-2 行情工具（对应 T2、T3、F3）

1. 结束日期不早于交易所当日时，不再报错，改为自动截到最近一个已收盘交易日。结果里返回：
   - `requested_end_date`；
   - `effective_end_date`；
   - `clamped: true`。

   截断后如果开始日期晚于结束日期，才报错，同时附上 `latest_allowed_end_date`。
2. 修正 Twelve Data 的边界：请求时把 `end_date` 加一天，再在本地过滤掉超出 `end_date` 的行。补一个固定样本测试，确保 12-31 这类年末交易日不再丢失。
3. 获取成功时把 `actual_first_date`、`actual_last_date`、`row_count` 一起返回给模型；来源标题改用实际覆盖区间。
4. 新增可选参数 `lookback_sessions` 或 `period`（`1m`、`3m`、`ytd`、`1y`），和起止日期二选一，由服务端按研究时钟换算成具体日期。
5. 所有工具的失败结果都附带可公开的 `message` 和结构化提示，例如 `latest_allowed_end_date`、`retryable`。不能只回一个错误代码。

### P0-3 抓取异常与中止（对应 R1、R2、T5）

1. 在 [openai_compatible.py](../../apps/api/app/openai_compatible.py) 的三处 `except (OSError, ssl.SSLError, HTTPException)` 前面加 `except _TransportFailure: raise`，保留原始原因。补测试：响应超过上限时，最终原因必须是 `source_too_large`，外部状态是 `returned`。
2. 给工具标注“只读、无副作用、不计费”的属性。网页 GET 和 SEC 公开接口的 `unknown` 结果，只作为这一个来源失败（`status: failed`，`reason: source_timeout` 或 `source_unavailable`）返回给模型，运行继续。会计费、有副作用的调用仍按现有规则对账，不自动重放。
3. 大 PDF 的处理（待定，二选一）：
   - (a) 维持 5 MB 上限，明确返回 `source_too_large`，并附上文件实际大小；
   - (b) 给 PDF 单独设一个可配置的上限（例如 32 MB），只抽取前 N 页，并标记“部分覆盖”。

   上限按内存和容器资源（512 MB）评估后确定。
4. 运行即使以 partial 结束，已获取但未读的来源也要进入版本，标为“已获取、未读”。不计入“已引用来源”，但下一轮的初始来源清单里要能看到。

### P1-1 无进展判定（对应 R3、R4）

1. 判断重复的签名加入已获取来源的集合。重复的获取请求，按“已获取”直接返回原来源 ID，并标 `reused: true`，`historical_prices` 也照 `acquire_sources` 的现有复用逻辑处理。
2. 同一批里只有部分调用重复时，只对重复的那一项返回 `duplicate_action`，其余照常执行。只有整批都重复、状态也没有变化时，才判定无进展。
3. 引文定位失败时，告诉模型原文是否在整个来源中出现过，以及最近一处的偏移；如果在已读片段之外，提示先读取那一段。

### P1-2 SEC 结构化数据（对应 T4、F1）

1. 标签和单位存在、但期间不匹配时，仍然入库，并返回 `period_match: none` 和最近 12 期 `{start, end, fp, fy, form, filed}`。
2. 获取成功时附带覆盖摘要：`latest_end`、`latest_filed`，以及最近若干期的列表，模型不用再按日期字符串去全文搜索。
3. 标签不存在时返回 `tag_not_reported`，与期间不匹配区分开。是否另加一个“列出该公司常用标签”的查询，按实际收益再定。

### P1-3 搜索与发现（对应 S1）

1. 跳转链接不再直接丢弃：在现有防 SSRF 检查的范围内解析到最终 URL，再按普通线索处理。与 plan.md 第 9 节第二阶段的这一项合并实施。
2. 抓取时从页面元数据（`article:published_time`、JSON-LD 的 `datePublished`）提取发布时间；没有发布时间的线索要明确标记。
3. `SYSTEM` 加固定规则：时效类问题在本次运行内先用发现来源工具查最近事件；结论依赖“最近”的数据时，要检查覆盖日期与研究时钟之间的差距。
4. 上一轮研究摘要带上没抓过的线索和失败的访问，下一轮可以接着处理。

### P1-4 缓存与压缩（对应 K1、K2）

1. L1 压缩加两条水位线：超过触发线时，一次压到触发线的约 60%（回落线）为止，这样后面多次调用都不用再压。
2. 设最小收益门槛：一次压缩省下的字符少于门槛（例如 8,000 字符）时跳过，不为了几百字符重置前缀。
3. 旧 thinking 按大块批量清理，并对齐到稳定的历史边界，不在每次调用时移动截断点。
4. 诊断数据按运行记录 `cache_read_input_tokens`、每次压缩的 `prefix_reset` 次数和节省字符数，并在验收报告里列出。
5. 跨运行首调用 0 命中（K2）单独做受控实验：同一题、同一模型，只改 `explicit_cache_control`（关 / 开），观察首调用的缓存命中。不预设 z.ai 支持显式缓存标记，以实测为准。

### P2 减少试错（对应 F2、F4）

- 上一轮研究摘要增加由事件确定性生成的 `tool_learnings`，例如：每个公司实际可用的 SEC 标签、已失败的请求、各来源的数据截止日期。只记录事实，不写模型推断。
- `growth_percent` 的参数改名为 `current_fact_id`、`baseline_fact_id`，或者在报错里写明顺序约定。
- 来自结构化来源（`historical_prices`、`sec_company_concept`）的事实，由服务端按来源元数据自动补全 `unit` 和 `currency`。

## 4. 不在本方案范围内

- 增加具体的指数、利率等数据类别，取决于许可和套餐，需单独确认授权后再改配置。行情工具本身的通用化（任意代码、OHLCV、盘中数据）见第 7 节。
- FRED 仍按项目约束不接入。
- 不针对“纳斯达克”或这道题写任何特例规则。所有修复都是通用工具行为。

## 5. 验证计划

1. **离线测试**：每个 P0/P1 项补单元测试，包括：时钟写入与续跑沿用、结束日期截断、Twelve Data 边界、超大响应的错误分类、只读失败后运行继续、未读来源进入版本、批内部分重复、SEC 期间提示、压缩水位线与最小收益门槛。
2. **受控真实复验**（预先登记）：
   - 固定条件：问题原文、模型和协议配置、工具权限、可用品种不变；不设运行预算（与线上一致），记录实际调用次数和 token。
   - 同一组条件跑 3 次，记录：模型版本、服务端缓存行为、搜索结果的变化（标为无法控制的因素）。
   - 观察指标：价格数据最新日期与最近已收盘交易日的差距、2026 年财报的使用情况、是否因单个来源失败而中止、无进展误判次数、总 token、缓存命中率、压缩次数，以及四个维度（传输、结构、证据、任务）的状态。
   - 修复项一次性合入的复验，只证明“问题已消除”，不用来比较单个改动的贡献。缓存实验（P1-4 第 5 条）单独做，每次只改一个变量。
3. 复验结论如实记录在 `src/docs/product/phase-a/` 下新的编号目录中。只有 partial 结果时不得称为通过；研究质量结论仍以独立、跨任务的验收为准。

## 6. 建议的实施顺序

1. P0-3 第 1 条（异常被吞，单点修复、风险最低）。
2. P0-2 的第 1、2、3、5 条，加上 P0-1。

### 7.2 原因

| # | 原因 | 证据 |
| --- | --- | --- |
| I1 | **研究工具集里根本没有盘中或报价工具。** | `historical_prices` 把 `interval` 写死为 `1day`（[research_historical_prices.py:95](../../apps/api/app/research_historical_prices.py#L95)），解析时只保留收盘价，开盘、最高、最低和成交量都丢掉了（第 131 行）。代码库里的 `market_provider.py` 也全是日线，而且没有接入研究 Agent。 |
| I2 | **只能查固定的三个 ETF，新上市的股票不在里面。** | 可查品种来自环境变量里写死的列表：QQQ、ONEQ、SPY。ANT 不在其中，模型连请求的入口都没有。新股上市当天要能查，就不能靠改部署配置。 |
| I3 | **当天收盘后的数据在结构上取不到。** | 规则是“结束日期不早于交易所当地今天就拒绝”，而美东当时还是 11-19，所以 11-19 收盘 5 小时后仍然不能请求。再加上 T3 的“结束日期不含当天”，要拿 11-19 必须传 11-20，这又一定被拒。所以现行逻辑下，任何“今天”的行情都拿不到，最多只能拿到前一个交易日。模型请求 QQQ 和 SPY 的 11-17 到 11-20，两次都失败。 |
| I4 | **错误只返回一个代码，模型误判了原因。** | 模型的理解是“授权价格源不覆盖这些日期”，于是决定“不再重试”，没有尝试改日期或换其他途径。 |
| I5 | **搜索只能找到新闻，找不到行情。** | 两次搜索共 14 条结果，8 条因跳转链接被丢弃。抓取工具只允许抓搜索返回过的链接，模型不能直接访问行情页；而且行情页大多靠 JS 渲染，就算抓到也拿不到结构化数据。 |

### 7.3 数据源本身是可以提供的（2026-11-20 实测，2 次 Twelve Data 调用，使用现有 key）

- **5 分钟线**：`time_series symbol=ANT exchange=NASDAQ interval=5min` 返回 52 根。第一根是 09:35 的占位数据（价格 83、成交量 0），真实成交从 11:45 那一根开始（开 111、高 114.99、低 110、成交量约 1.61 亿股），最后一根是 15:55（收 96.91）。
- **日线**：返回完整的 OHLCV：开 111.5、高 115.10、低 92.72、收 97.17、成交量约 8.52 亿股。传 `end_date=2026-11-20` 才返回 11-19 这一天，再次印证 T3 的边界问题。
- **报告因此缺了什么**：
  - 实际开始交易的时间（约 11:45 ET，不是 9:30 开盘）；
  - 全天最低价 92.72，以及收盘前跌破发行价溢价区间的走势；
  - 全天成交量；
  - 最高价的口径差异：CBS 写 114.99，交易所日线是 115.10。这类差异正需要行情数据交叉核对，只靠新闻没办法发现。

### 7.4 修复项（与第 3 节合并实施）

**P0-4 通用行情工具**（替换或扩展 `historical_prices`）：

1. **参数**：
   - `symbol`：服务端通过供应商的代码检索确认交易所、币种、证券类型，不要求预先写进配置；
   - `interval`：`1min`、`5min`、`15min`、`1h`、`1day`；
   - 时间范围：起止日期，或第 3 节 P0-2 的 `lookback`。
2. **输出**：保留完整的 OHLCV，并标注时区和价格调整口径。过滤成交量为 0 的占位 K 线，在结果中计数说明。返回实际首末时间和首笔成交时间。
3. **权限**：从“逐个品种白名单”改为按许可策略控制：允许哪些交易所、证券类型和时间粒度，以及各自的 store、display、model_input、export 权限。授权仍由配置决定，不因为模型提出请求就扩大。盘中数据的使用和展示许可需要先按 Twelve Data 现行套餐条款核验（见 7.5）。

**P0-5 交易时段感知**（替代 [research_historical_prices.py:93](../../apps/api/app/research_historical_prices.py#L93) 的一刀切拒绝）：

1. 按交易所的时区和收盘时间（先用常规时段，之后接入交易日历）判断当天是否已收盘。
2. 已收盘：当天日线可以返回，标记为 `session_status: closed`，并注明供应商之后可能修订。
3. 交易中：盘中 K 线返回到当前时间减去供应商延迟为止，标记为 `intraday_unfinalized`；当天日线不能当作收盘数据。
4. 研究时钟（P0-1）同时提供各交易所当前的时段状态，模型因此能理解“今天”是否已经收盘。

**P1-5 新闻与行情交叉核对**：

1. `SYSTEM` 加固定规则：报道里的价格、涨跌幅、成交量，有行情数据时必须与行情数据核对，并在报告中列出差异和各自口径。
2. 行情工具暂时不可用时，报告明确写“价格仅来自报道、未经行情数据核对”。本次的缺口文字已经这样写，保留。
