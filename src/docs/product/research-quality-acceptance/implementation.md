## 怎么看这些结果

最后一轮按业务链集中验收，在同一进程运行九个后端测试文件，覆盖原生运行器、正常 API、证据需求、金融计算、交付组装、正文核验、取消与版本保存，197 项通过。此前六文件的 99 项回归还把异步线程异常作为失败处理。测试包含同币种跨数量级的成功换算及换算记录缺失时降级的对照。主题页、证据视图与 Markdown 交付三个前端测试文件合计 52 项通过。Web 全量 TypeScript 检查通过；为完成这项检查，修正了管理页两处可选请求头的类型表示。OpenAPI 与生成的研究类型均通过漂移检查。各组测试覆盖有交集，数量不相加作研究成功率。

- **确定性判定。** 在同两条收入已答、EPS 缺失的工具轨迹上，缺证误报完成从 2/2 变为 0/2。财务齐全、缺项、市场齐全、重复标的及定性和时点问题另有原生运行器回归。这些运行使用受控工具调用。部分测试用等价的中英文短文或可执行的行情回执验证行为，不作为 8 个冻结资料上真实模型的准确率。[双判定原始记录](e2-replay.json)
- **连贯业务链。** 正常入口 API 单进程 16/16 通过；分开验证的预算、恢复、取消及逐项事实契约与其中部分路径重叠。PostgreSQL 三项恢复及并发准入通过，另有取消后跨进程重开和导出。Chrome 使用真实页面与固定 API 回包；持久化由独立真实 API 与数据库链验证。宿主缺中文字形，浏览器验收覆盖交互和 DOM 文本。[恢复记录](e4-evaluation.md) · [浏览器环境](browser-delivery-2026-11-23.md)
- **真实调用。** E1 在冻结候选上完成 4 题 × 2 臂 × 2 次，共 16 次运行、42 次模型调用和 746,065 个已报告 tokens。全部运行停在部分完成，12 次输出截断，4 次耗尽实验调用上限。按预登记核心项，计数反馈臂有据回答 3/16，证据缺口反馈臂 5/16。缓存状态、有限样本和相对交易日文本限制了推断。费用未知。[E1 逐题判读](e1-evaluation.md) · [逐次结构化记录](e1-index.json)
- **主张绑定实验。** E3 对比两种提交形式。两组均使用合成资料；E3 的 B 臂输出文本绑定，不计作服务端已验证的事实 ID。E3 三次成功共 2,248 tokens，第四次返回 ProviderFailure，耗时 231.485 秒，超过预登记的 90 秒边界；具体原因与费用未知，按协议停组。该组不足以判断准确率、解释质量或单位成本改善。[E1 预登记](e1-preregistration.md) · [E3 实际输出与判读](e3-evaluation.md)
- **适用边界。** 实体、指标和意图的自动匹配仍有语言和资料覆盖范围。可定位的引文可能只说明相关性。正式多任务独立评估、语义复核和单位有效成果成本尚需独立证据。来源撤权后，系统会隐藏可能混合多个来源的自由正文，保留仍有完整可展示引用链的分项。

## 验收中修正的问题

- 实际把 worker 终止在“已保存提交检查点、尚未写入正式版本”之间，发现交付成功后的原键重试被父版本检查提前拒绝。现在先在原账户与原运行内校验原请求，已受理的键返回原恢复操作。新键继续检查当前父版本。隔离 PostgreSQL 复验得到一个子版本，原始两次模型调用后没有新增外呼。[强杀与幂等复验](e4-evaluation.md)
- E1 冻结候选在收入与 EPS 的真实工具轨迹里，为同一个 EPS 分项保留了一行已答和一行待答，还给已答的收入行附了自动生成的未答理由。工作树已统一两处切分结果的匹配，自动占位理由不再覆盖证据判定，已保存的残缺答案也不能把核心要求升级为已满足。真实对照继续使用原冻结候选，实验记录保留原输出。
- 使用原始工具返回的事实与计算，离线重放了 E1 中 D1-A1 和 D2-A1 的交付。D1 从三行矛盾状态收敛为两个有计算引用的已答项。D2 保留已答的收入增长和仅有本期数值的 EPS，准确指出缺 2024 年同口径的稀释 EPS。这两次重放验证工作树上的交付修复，没有重新调用模型。[真实回执重放脚本](replay_e1_delivery.py)

## 后续实验：小批记录事实能否提高交付率

E1 的 12 条截断中，11 条停在读取整份资料后的第二次模型调用，1 条停在保存三项事实和收入增长计算后的第四次调用。原始 E1 产物只能确定工具边界，失败响应里具体出现过哪个工具没有留存。[逐条定位](fact-batching/trace-audit.md)

新对照使用冻结 E1 的证据缺口反馈、相同模型及工具、相同四题和预算，A 沿用原策略，B 仅增加每次最多记录两项事实、读取回执后再记下一批的指令。每题每臂重复两次。两臂的正式提交率均为 0/8。按已保存证据可复核的核心项，A 为 6/16，B 为 7/16；八个配对中 B 有四次更好、三次更差、一次持平。B 少两次截断，同时多两次耗尽四调用预算，已报告用量增加 20.3%。该结果不足以支持将分批作为默认交付策略。[预登记](fact-batching/preregistration.md) · [逐轨评分](fact-batching/scoring-results.json)

新实验的八次截断都返回了 `max_tokens`。在可观察的解码响应里，五次只有 `thinking` 类型的内容块；三次出现工具块，其中仅一次出现 `record_facts`，该调用没有执行。下一步若以正式提交为目标，宜单独验证“最后一个可用模型调用优先提交已有证据与明确缺口”这一变量，保留此次冻结题目和预算作对照。[截断与工具回执](fact-batching/mechanism-conclusions.md)

## 后续实验：最后一次调用优先提交

两臂均恢复原事实记录策略，B 只在第 4 次调用追加优先提交现有证据并明确缺口的指令。已执行七对，正式提交 A 0/7、B 0/7。以每次两个预定义核心项为分母，已保存证据支持 A 4/14、B 0/14。B 仅两次到达末轮，均为 D1；两次末轮输出都截断，其中一次返回了未执行的提交工具块。D4 的首次 B 请求被服务方拒绝且结算未知，按预登记停止，最后一对未启动。[执行与冻结条件](last-call-submission/execution.md) · [逐题评分](last-call-submission/scoring-results.md)

14 次均未进入提交处理器，正式提交中的漏答率无法估计。检查被动保留的分项时发现，四个已有事实及计算充分支持的核心项中，有一个已保存的 EPS 增加 1 美元未完整呈现。另有五个核心项的原文明确写出了资料缺口，分项没有把具体缺口交代清楚。该层审计检查运行器产物，未对本批次进行独立的界面呈现验证。[漏答与完成误判专项审计](last-call-submission/audit-results.md)
