# 计算契约配对与读后请求检查（外呼前登记）

D1–D4 各两次重复，串行 ABBA。两臂使用同一份本轮交付修复、原事实策略及历史 observer 的 A 路径，无末轮追加提示。唯一处理因素为 calculate_financials 的模型可见契约及其对应执行语义。A 将基准 Git 82900b4b 中 CalculationPlan 与 _exec_calculate_financials 两个定义覆盖到共同代码，B 使用已验收实现。版本清单和代码压缩包在运行前写入。运行时记录实际向 provider 提供该工具的轮数，并区分模型选择工具和处理器实际接受。阶段二若需修改同一文件的其他定义，两臂共享这些修改。历史实验不混作 A。

使用 E1 的 cases.json、构造器及非密钥配置摘要。模型 glm-5.3-flash，原生 anthropic_messages，每轨 4 调、160000 核算 token、2048 输出、180 秒总时限、90 秒单请求、零搜索、无预发送重试及附加采样设置。按原批规则在未知外部状态/结算、服务错误或硬时限停批，不补跑或选择性丢轨。已启动即入分母。核算预留、实际报告量和实际费用分列，未取得的数值记未知。原批未知结算维持原样。

正式提交要求处理器接受回执与保存的 submission 一致；单个工具块或被动 partial 均不计入。每个已启动轨按旧评分协议中的两个核心项计分。逐项区分保存的证据、经验证在用户终态可见的回答，以及已接受正文中的呈现。分析全部 8 个配对和资源账本；未知不计入确定改善。逐轨记漏答、错误完成和正负项，通过全部证据语义再确认结果。模型服务版本、缓存及实际费用可能不可锁定。不使用开发样本给出总体质量结论。

读后诊断按 E1、事实分批、末轮指令三批分别记录。对冻结 E1 构造器，离线重放第一轮已执行读取，观察第二轮完整 wire 中每段原资料的精确副本及 UTF-8 字节占比，保留区间、结构路径、哈希和计数。历史 raw wire 不可得，列出重建的 turn 是否与旧哈希一致。将原始读后请求中重复的资料内容与重复工具参数或提示区分；只有复现可删除的资料副本并验证剩余内容和定位完整，才登记单独去重对照。此方法不能排除任意语义改写。

隔离两个实验树时，以已核验的 E1 代码包提供历史工具、事实记录、系统提示、读后上下文与协议适配。两臂共用本次交付评估与所需计算依赖。计算工具 A 使用启动时 82900b4b 的旧输入和执行实现，B 使用本次修复实现。两者都包含当前计算器已有的贡献率公式。无关协作者的事实记录、搜索及 UI 在途改动不进入实验。对四道题取完整首轮 Messages 请求哈希，遮盖 calculate_financials 的 input_schema 后应逐题相同，同时核验该工具原始 schema 确有差异。

读后审计的实际入口为在实验目录中运行 `read_audit.py <历史结果根目录> <输出JSON>`，PYTHONPATH 使用已通过 verify.py 的 E1 `apps/api` 和冻结的 `prior.py` 所在目录。实际外呼批次先运行 `python3 prepare.py <新的冻结目录>`，在已授权的模型环境中用 API 虚拟环境执行冻结目录的 `batch.py`。它会先执行离线预检，再一次性按登记启动。历史目录永远不作输出目录。
