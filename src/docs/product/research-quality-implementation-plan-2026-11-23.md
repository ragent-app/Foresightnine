# ForesightNine 研究质量改进实施方案

2026-11-23 · 方案稿 · 代码核对基线 `879de1d`，另检查了当日工作区中正在开发的分项答案和恢复改动。

## 1. 交付目标与优先级

用户打开一次研究，应当能看出原问题的每一项答到了哪里、最重要的依据是什么、哪些判断仍靠假设，以及中断前取得了什么。保留单协调者与串行工具循环。第一轮改动集中在服务端如何认定证据、如何据此交付。默认入口仍只需问题或资料。

| 顺序 | 用户可见的改进 | 代码或运行依据 | 实施出口 |
| --- | --- | --- | --- |
| 1. 证据是否够用 | 看得到每个关键问题取得的对应证据 | 当前 IPO 基准检查可由两次成功行情调用满足，普通成功搜索也可计入反证动作。[覆盖与反证判定](../../apps/api/app/research_run_insights.py) | 错主体、错期间、重复调用不能填平证据缺口 |
| 2. 完成状态是否准确 | 已回答与未回答的分项同时可见 | 现有测试中，询问业绩和 EPS，只回答收入，收到提示后原样重交仍为完成。[提交测试](../../apps/api/tests/test_research_runtime_attention.py) | 原样重交能结束运行，成果准确显示为部分完成 |
| 3. 核心判断能否复核 | 从数字、对比或解释能追到对应材料 | 当前提交分开接收报告正文和带引文的主张，逐条定位引文。正文核心判断的支持关系仍需建立。[提交契约](../../apps/api/app/research_tools_registry.py) | 关键数字可复算，推断标明证据与条件，超出依据的归因可识别 |
| 4. 中断后能交付多少 | 重开时可读已核实分项，可安全继续剩余问题 | 旧版六次实跑中两次完成、两次模型故障后部分完成、两次受环境资源争用影响失败。该批次未评估研究质量。[365 复验记录](phase-a/365-s0-real-model-revalidation/evaluation.md) | 中断、恢复、重开、导出各路径交付同一版本的可用成果 |

这四项是现有 M1 研究闭环与 M2 恢复工作的细化。第 1、2 项构成首个可交付切片，第 3、4 项复用同一份证据状态。当前 [交付整改验收协议](research-delivery-acceptance/protocol.md) 已有断流、批量事实录入与表格的独立对照，本方案沿用其合适的回放材料，新增覆盖与完成状态实验。已有实验保留原预登记口径。

## 2. 从问题到答案的执行路径

1. **运行准入。** 从既有研究入口取得用户问题、父版本、授权来源、研究截止时间及可用工具。提问、资料概括、追问和指定引文复核走同一入口。给单问题直接创建一项；复合问题保留原文与各子句的对应位置。用户明确要求的子句均为核心项。
2. **建立证据需求。** 按问题选择已有方法包，从中实例化适用的核验条件。没有匹配方法包时，直接从问题形成最小需求。优先在原有模型轮次内提出分项和取证意图，服务端分配 ID、核对原题范围并保存；缺少可靠拆分时保留整题为待核对核心项。后续能新增发现的依赖，保留增改理由。模型不能静默移除用户的要求。
3. **执行并绑定证据。** 模型选择下一动作；读取、取数、计算照旧由工具完成。服务端从实际回执和研究对象识别实体、口径、来源版本与覆盖范围，将可用结果绑定到对应分项。工具失败只更新尝试记录、能力和阻塞原因。一次工具调用可产生多个相关证据，一条证据也可支持多个分项。
4. **选择下一步。** 工具反馈附带发生变化的分项、未满足条件、已失败路径和可能有效的下一动作。优先处理会改变核心答案的缺口；可在现有资料中解决的先查已有资料。授权关闭、上限耗尽、重复相同动作没有新增证据时，交付已有结果。省略预算仍表示未设，实验限额只应用于实验。
5. **提交与版本化。** 服务端对同一份证据状态重新求值，得到分项结果、核心判断引用和整体状态。运行结束原因、外部调用结算与答案完整度分别记录。Web、历史版本和导出读取该次已提交的结果；追问引用父版本并增补，用户确认的判断保留原版本及复核记录。

## 3. 第一优先级的证据契约

以下是拟议的最小字段和归属，字段名在实现时可与现有模型合并。沿用现有 `ResearchQuestionPart`、`ResearchClaim`、`ResearchFact`、`ResearchCalculation` 及原文定位。证据引用指向账户、主题与版本范围内的真实对象。[研究对象模型](../../apps/api/app/research_topics.py)

| 对象 | 最小字段 | 写入与校验 |
| --- | --- | --- |
| 问题分项 | 稳定分项 ID、原题片段、核心或辅助、关联需求、阶段答案、待解决事项 | 首次运行分配 ID；续跑与重提同一动作复用 ID。核心项涵盖用户明问及形成该结论的必要前提，方法包其余提示按适用性处理 |
| 证据需求 | 需求 ID、分项 ID、检查类型、适用理由、目标实体或实体角色、指标、期间或窗口、单位与口径、允许的证据类型 | 方法包提供可复用条件；具体值来自原题、已解析实体与研究时点。题目未指定的基准或口径须记录选择理由 |
| 证据绑定 | 需求 ID、来源版本和原文跨度或结构化观测、事实 ID、计算 ID及其输入、当前或父版本出处 | 由服务端验证引用存在、已读范围、账户权限、资料时点及计算输入。已撤权、过期或条件不匹配的证据返回具体缺口 |
| 需求判定 | 已满足、部分满足、未取得、来源受限或不可用、有实质冲突、不适用；附理由、缺少的条件与证据引用 | 每次相关结果到达重新判定；不适用须给出可核对理由，服务故障记为不可用。新证据可使原本满足的需求重新出现冲突 |

**首批只实现能跨任务复用的检查。**

| 检查 | 满足条件 | 必须检出的反例 |
| --- | --- | --- |
| 同口径财务比较 | 主体、指标定义、期间长度、合并范围和币种／单位可比；规范化保留转换过程。增速绑定两个有序输入及已保存的公式 | 拿收入回答 EPS；用累计半年数当单季；用基本 EPS 和稀释 EPS 跨期直接比较 |
| 标的与基准表现 | 标的和基准角色明确，标识正确，采用双方实际共同交易日、可比价格调整口径和同一定义的回报；披露取值与窗口 | 同一标的查两次；两个结果只有一个共同价格点；把发行价至收盘与指数开盘至收盘称为同口径超额回报 |
| 时间、来源与冲突 | 资料在截止时点可用；引用标明来源版本、实际数据日期和口径。用既有聚类识别转载，用既有口径核对识别修订或实质差异 | 截止日后才发布的修订数据；三篇转载被当成三个独立确认；无法解释的重大差异被合成一个精确数值 |
| 替代解释与反证 | 标明针对哪条判断、哪个替代解释、做过哪项定向检查、发现及其来源。若无发现，记录查过的范围、结果与限制 | 泛搜同一公司就算完成反证；仅有标题就宣称反方不存在。单值摘录题可标明本项不适用 |

对来源缺失要依原题判定。例如，若用户问“这份公告有没有披露 EPS”，核实完整相关范围后，“公告中未披露”可以是完整答案；若问“EPS 是多少”，同一结果只能证明资料有缺口。只读过部分章节时，答案应限定为“已检查章节未见”。纯文本公告的条款、日期或限定语可以使用已定位引文，避免强迫定性任务先造数值事实。

## 4. 第二优先级的提交与状态决定

沿用已有 `completed`、`partial` 研究状态。模型建议提交时，执行器依次校验来源与引用、求值核心需求、检查拟展示判断，再决定补证或交付。[当前提交与补证逻辑](../../apps/api/app/research_tool_executor.py)

| 提交时的情况 | 后端动作 | 用户看到的结果 |
| --- | --- | --- |
| 核心项均有可复核答案；剩余是辅助背景 | 结束并保存各项依据，附辅助限制 | 完成 |
| 核心项有缺口，仍有已授权且可行的补证动作 | 首切片沿用现有最多一次提交前提醒，列出缺哪项、缺哪个条件、可用路径；同一证据状态只提醒一次 | 运行中；再提交时重新评估真实结果 |
| 提醒后原样重交；或预算、权限、可用来源已阻止推进 | 结束运行，保存支持得住的分项、具体缺口、停止原因 | 部分完成；有答案的子项照常可读 |
| 冲突影响最终答案 | 能解释口径则并列证据及解释；仍无法判定则保留两边材料。若原题就是核实是否存在冲突，已证明冲突可满足该项 | 按原问题的完成度展示冲突及影响 |
| 请求取消、传输失败或外呼结果未知 | 走既有生命周期与对账路径，从最近的持久检查点组装可用结果；尚未取得的内容显示缺口 | 操作状态及停止原因与已取得的研究成果分别展示 |

服务端不得把缺失的核心项仅因模型在“限制”写过一句话就判为已回答。对模型主动提交 `partial` 保留其限制，不自动升级。若判定器内部异常，记录诊断并将无法评估的核心项标为待核验。持久化阶段若拒收了某个对象，必须在最终可保存的对象集合上重算依赖它的分项与完整度，避免出现报告显示完成、引用已被剔除的版本。

**端到端样例。** 用户问“比较两年收入增长，并说明稀释 EPS 如何变化”。示例资料提供收入 120 和 100 百万元，仅披露本年稀释 EPS。第一项展示 `(120−100)/100 = 20%`、两个输入及出处；第二项展示本期数值与“缺少上年同口径 EPS”。整体为部分完成。补入上年年报后，追问或可安全继续的运行引用原事实并补算差异，保存新版本。用户可分别查看当时的答案和补证后的答案。

## 5. 第三优先级的正文与主张

- **事实和数值。** 给回应核心分项的判断一个可回查的主张 ID。已披露数字绑定事实，衍生数字绑定计算或行情分析输入及计算结果；文字披露绑定已读原文。核验数值、方向、单位、期间与主体。表格和图表继续沿用已创建对象及其权限。
- **解释与假设。** 对核心解释记录支持它的观察、从观察到结论的推断、最能削弱它的已知证据，或仍需验证的条件。例如，“毛利率下降”可以由两期数据和计算支持；“定价权减弱导致下降”还需要价格、组合或管理层归因等材料。资料只支持相关性时，写明可能解释。对无法确定的语义支持保留待核验状态。
- **生成和阅读。** 结构化分项、结论与证据共用一份结果；正文核心段引用稳定主张 ID，服务端解析引用并校验归属。用于回答核心问题的数值和结论优先由已保存分项渲染，避免散文再生成一套数字。Web 从结论跳到计算输入或来源上下文；导出采用现有权限策略及同一版本引用。分项本身也要追溯派生来源，避免在部分答案中泄露受限材料。
- **验收。** 设置原文真但推断过强、正反方向写反、数字正确但期间错、定性条款正确、对照证据冲突五类样本。分别查“能否定位”“引用是否支持判断”“推断是否充分限定”。机械核验无法定性的项目列为未评估；若以后试验模型审阅，单独核算增益与误报。

## 6. 第四优先级的中断、追问与恢复

在已有工作区分项检查点上扩展引用类型和稳定 ID。事实保存、计算成功、冲突出现、分项答案更新时，刷新受影响分项；可由代码推导的状态随工具结果一起持久化，减少专门用于记账的模型外呼。将分项版本与现有检查点、批次游标关联，重复回执按既有调用和对象 ID 幂等合并。[研究运行器](../../apps/api/app/research_runtime.py) · [版本写入](../../apps/api/app/research_turn_persister.py) · [恢复与对账](../../apps/api/app/research_recovery.py)

| 中断位置 | 恢复或重开后必须能看到／验证 |
| --- | --- |
| 第一项证据已保存，第二项尚未取证 | 已取得的事实及来源、对应的分项进度、尚缺的材料。缺少足够依据的分项保留待答 |
| 计算已保存，尚未生成正文 | 从已保存输入和公式展示可验证的结果；复算一致。恢复后沿用已有记录，幂等重放不产生重复对象 |
| 提交前、版本写入期间或同主题有并发编辑 | 同一次提交得到一个一致结果；父版本变化按现有冲突规则处理。用户已确认判断保留历史，新增 Agent 判断可追到父版本 |
| 外部请求已发出、结果或费用未知 | 保留已完成部分并记录待对账，不自动再次外呼。恢复后重新校验当前账户、绑定配置、来源版本与权限 |

Web 重开、版本详情、进度与导出分别测试。运行中页面可展示正在核验的状态；正式版本只展示已保存结果。在跨账号、来源撤权、限制导出等用例中，检查报告、分项、引文、图表和下载各条路径。

| --- | --- | --- |
| A. 固定起点 | 现有方法包、运行测试、当前工作区的交付整改协议 | 记录纳入对照的代码与未提交变更指纹、任务、输入快照、已知期望。重放旧版误判；单列已有修复和未评估项 |

| E. 恢复与集中验收，复用 B–D | `research_recovery`、研究检查点、主题版本、操作存储、验收脚本 | 以上中断矩阵、持久存储重开、幂等与权限回归、冻结对照结果。恢复正确性从 B 起随实现检查，最终在此集中验证 |

实施前复核分项交付分支的实际落点，直接复用已合入逻辑。各工作包分别提交可审阅的代码、契约变更和对应证据。开发期直接演进内部结构，保留当前运行的安全恢复与版本追溯。项目主路径继续按 wire API 配置模型。

## 8. 测试与受控实验

**先验证判定逻辑。** 用固定工具回执和持久存储集成测试覆盖第 3–6 节所有反例，并加上完整的正例。首切片至少有四个对照：收入和 EPS 均齐全／只缺 EPS；同窗口有效基准／同一标的重复两次。附加边界包括只给定性材料、不同财政年、非同币种、合法空来源、显式零预算、撤权、历史资料截止、未知外呼、父版本冲突。对照复用当前测试入口，修改旧的“忽略提醒后仍完成”断言，同时保留“提醒最多一次”和“不会无限重试”的保证。具备确定答案的离线断言须逐项通过。

**再测模型行为。** 建议第一批用 8 个冻结问题，每类 2 题，涵盖财报比较、事件表现、定性公告和宏观或跨期冲突。开发样本与独立保留题按来源和问题分开；保留题在评估前冻结答案、可接受替代证据、核心／辅助要求及判据。小样本用于识别机制性差异。阶段 B 的正式质量对照另按总计划建立独立任务集与基线。

| 实验 | 唯一主要变量 | 固定条件与观测重点 |
| --- | --- | --- |
| E1 证据是否取全 | 工具计数式覆盖反馈 vs. 按实体、期间与证据绑定的反馈 | 相同模型、工具接口、初始提示、提交策略与数据快照；反馈内容随处理策略变化。看关键证据覆盖、无关调用、错配与遗漏 |
| E2 完成是否诚实 | 一次提示后的旧完成策略 vs. 服务端按分项决定完成度 | 先对相同证据状态和相同提交做双判定，无需额外模型调用；再用相同提示策略检验正常结束和补证。看漏答误判完成、齐全误判部分完成 |
| E3 主张能否复核 | 原正文提交 vs. 核心判断绑定证据的提交形式 | 复用冻结证据包，固定问题、模型和生成参数；仅调整被测的提交契约及必要说明。看主张支持、数值一致性及新增成本 |
| E4 中断保留率 | 在同一冻结轨迹上比较现有恢复与分项恢复交付 | 故障点、输入、回执和权限相同，先做离线注入和 PostgreSQL 重开；复用已有恢复对照。看已核实答案保留、重复外呼、跨版本误关联 |

真实调用前将每组的模型和协议、服务实际支持的参数、提示和工具 schema 指纹、资料哈希、许可、调用及 token／时间／费用预算写入预登记；费用无法核实时记录未知。可从 E1 的两类首切片各 2 题起步，每题 A、B 各跑两次，交替 AB／BA，共 16 次运行。对每组设置相同实验预算，以冻结任务可完成的基线用量定值；预算数值在首个外呼前锁定。实验资料使用获授权快照；需要研究动态检索时单独成组，记录检索漂移。受限来源遵守既有策略，FRED 继续禁用。实验过程中保持环境稳定，避免同机高负载验收混入结果。

**判读指标。** 逐题保留分子、分母和失败轨迹，按以下顺序判断变化。

| 指标 | 定义与用途 |
| --- | --- |
| 缺证误报完成率 | 核心要求未满足却标为完成的运行数 ÷ 按冻结答案确有核心缺口的运行数 |
| 齐全误报部分完成率 | 核心要求均已满足却标为部分完成的运行数 ÷ 按冻结答案已齐全的运行数。与上一项共同防止一律报部分完成 |
| 关键问题有据回答率 | 给出符合原问题且证据合格的核心分项数 ÷ 冻结任务的全部核心分项数；另列因真实来源限制而无法回答的项 |
| 引文定位与主张支持 | 对可评估的核心主张分别统计成功定位、引文支持、计算可复算的数量与各自分母。纯定性语义缺乏独立评估时标为待核验 |
| 中断成果保留与重复执行 | 重开后仍可核验的分项 ÷ 故障前已经核实且仍有权限的分项；另列外呼意图、未知回执、重复计费及权限违规 |
| 成本与可用性 | 逐次记录模型、搜索、工具、用时、已知用量与费用；按有据回答的核心分项核算单位成本。零有效分项与未知费用单列 |

每次运行都进入执行统计；传输或基础设施故障单列原因。对无法评价的语义或分母为零的指标写“无法判定”，并公开可评估数。预先冻结确定性用例的期望结果；正式质量阈值按项目约定在独立基线具备后、盲测前确定。人工复核未取得时可以完成工程验证，证据状态如实保留。

## 9. 完成条件

首切片交付时，应能从 Web 输入复合问题，分别得到完整、缺一项、来源受限和中断的结果；每项可沿引用核查，状态在页面重开与允许的导出中一致。研发侧留存用例、判定差异、失败和恢复记录。扩展到其他方法包前，先核对独立题上两类完成误判及有据回答率，确认收益来自证据和判断改善。进入阶段 B 正式验收时，沿用总体计划的真实资料、独立跨任务及失败恢复要求；发布依项目既有授权处理。
